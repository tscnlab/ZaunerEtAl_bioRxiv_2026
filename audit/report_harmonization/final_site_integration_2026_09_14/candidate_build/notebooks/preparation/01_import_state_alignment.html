Preparation 01: Import and align light, sleep, and wear data

From fixed site releases to checked one-minute measurement records

Last modified:

August 13, 2026

Purpose and position in the analysis chain

Preparation 01 establishes the measurement record that all later preparation steps use. The production workflow reads the fixed light-logger, sleep-diary, and wear-log releases from nine study sites. It checks their identities, converts the logger observations to complete one-minute values, preserves both actual and local clock time, and assigns a measurement context to each minute. Its outputs enter Preparation 02, where hourly and daily coverage is assessed.

The scientific inputs are 35 fixed local source files: light-logger, sleep-diary, and wear-log files from recorded site releases. Their exact release identities and file checks are documented in the technical sections at the end of this page.

1. Establish the exact source files

The production import uses one recorded release per site. Table Table 1 shows the human-readable site names in the submitted-manuscript order. The source audit contains four inputs per site (sleep diary, wear log, near-eye light, and chest light), except Tübingen (DE), where no chest logger file is part of the study input.

2. Preserve actual time and local clock time

Two time coordinates are retained because they answer different questions. datetime_utc identifies the actual instant and is used to order readings and measure elapsed time. datetime_wall represents the local clock reading, so 08:00 has the same time-of-day meaning at every site. At an autumn clock change, one local minute can correspond to two actual instants. The stored audit contains 360 such participant-level wall-clock minutes—120 for Madrid (ES) near-eye data, 120 for Madrid (ES) chest data, and 120 for Tübingen (DE) near-eye data. They remain distinct in UTC and are not discarded or averaged during import.

The original logger interval is inferred separately for each participant and placement. A one-minute value is retained only when all expected original readings in that minute are present and finite. Table Table 3 shows the resulting regimes; the production audits recorded no incomplete original-reading schedule.

3. Prepare sleep and wear periods

The sleep diary defines the interval from sleep preparation to wake. Its start is included and its end is excluded. These measurements characterize the bedside sleep environment and remain part of the intended hybrid 24-hour record. The wear log supplies additional context. An off label while awake is treated as true non-wear; sleep and site_leave labels are retained for provenance but do not independently remove a light value.

Valid intervals are stored for later projection onto complete participant-day grids. Twenty-two sleep-derived records could not define a supported wake interval and are listed with participant, source rows, bounds, and reason in state_interval_audit.csv. They were not silently repaired. No wear-log interval required review.

4. Align measurement context without losing rows

Sleep and wear periods are matched to each one-minute light record using participant and actual time. All 17 site-placement joins retained their input row count. A missing wear-log label is not interpreted as non-wear. Table Table 6 therefore reports missing wear information as provenance, not as an automatic exclusion.

5. Apply the melEDI operating limit

The valid melanopic equivalent daylight illuminance operating range is strictly below 100,000 lx melEDI (ActLumus User Manual 2023). Values at or above that boundary remain in the stored raw channel and receive an explicit flag, but the analytical melEDI channel is unavailable for that minute. The rule does not remove illuminance solely because melEDI reached its limit.

6. Stored sample after import and alignment

The result is a complete set of one-minute grid rows for every imported participant stream. A grid row can contain an unavailable signal because of missing original data, non-wear, or the melEDI operating limit; therefore grid rows and valid signal minutes are reported separately.

Near-eye and chest measurements remain separate. Chest measurements are a complementary placement and are not pooled with the near-eye data.

7. Checks that had to pass

The 35 fixed source files are recorded in pinned_downloads.csv. Their repository revisions, DOIs, URLs, byte sizes, and SHA-256 digital fingerprints are propagated to source_audit.csv. A SHA-256 fingerprint establishes file identity; it does not describe scientific contents.

NoteWhat is calculated during this render?

This report reads already stored CSV manifests and audits. During rendering it checks the existence, byte size, and SHA-256 fingerprint of every listed Preparation 01 artifact and fixed source file; checks the columns needed for the displays; and calculates only compact descriptive totals from stored audit rows. It does not retrieve a source file, import logger data, aggregate a minute, align a diary or wear period, replace a signal value, rebuild an artifact, or run the production verifier.

The stored audits expose the checks performed during production. Rendering does not rerun their producing verifier; it confirms the identities of the stored evidence and summarizes the recorded outcomes.

Production scripts and why the operations are separate

The producing code is listed in execution order in Table Table 12. Separating source identity, temporal aggregation, interval preparation, state matching, and verification leaves a stored checkpoint at each scientifically consequential boundary.

Exact artifacts passed to Preparation 02

Preparation 02 receives the two combined one-minute files and the checked state intervals. The intervals are needed because Preparation 02 inserts explicit missing-minute rows before calculating coverage; known sleep, wake, and non-wear periods must also be assigned to those inserted rows.

```{r}
absolute_path <- function(path) {
  ifelse(grepl("^/", path), path, file.path(root, path))
}

read_stored_csv <- function(path) {
  full_path <- absolute_path(path)
  stopifnot(file.exists(full_path))
  readr::read_csv(full_path, show_col_types = FALSE)
}

assert_columns <- function(data, required, label) {
  missing_columns <- setdiff(required, names(data))
  if (length(missing_columns) > 0L) {
    stop(
      label,
      " is missing required columns: ",
      paste(missing_columns, collapse = ", ")
    )
  }
  invisible(data)
}

prep_gt <- function(data, source_note = NULL, groupname_col = NULL) {
  output <- gt::gt(data, groupname_col = groupname_col) |>
    gt::opt_row_striping() |>
    gt::sub_missing(missing_text = "—") |>
    gt::tab_options(
      table.font.size = gt::px(13),
      table.width = gt::pct(100),
      data_row.padding = gt::px(4),
      heading.align = "left",
      source_notes.font.size = gt::px(11)
    )

  if (!is.null(source_note)) {
    output <- output |>
      gt::tab_source_note(gt::md(source_note))
  }
  output
}

manifest_objects <- vector("list", nrow(manifest_registry))

for (index in seq_len(nrow(manifest_registry))) {
  manifest <- read_stored_csv(manifest_registry$Manifest[index])
  assert_columns(
    manifest,
    c("path", "sha256", "bytes"),
    manifest_registry$Manifest[index]
  )
  listed_paths <- absolute_path(manifest$path)
  exists <- file.exists(listed_paths)
  observed_bytes <- rep(NA_real_, length(listed_paths))
  observed_sha256 <- rep(NA_character_, length(listed_paths))
  observed_bytes[exists] <- file.info(listed_paths[exists])$size
  observed_sha256[exists] <- vapply(
    listed_paths[exists],
    digest::digest,
    character(1),
    algo = "sha256",
    file = TRUE
  )

  manifest_checks[[index]] <- tibble::tibble(
    Stage = manifest_registry$Stage[index],
    `Files listed` = nrow(manifest),
    `Files present` = sum(exists),
    `Size checks` = sum(exists & observed_bytes == manifest$bytes),
    `SHA-256 checks` = sum(
      exists & observed_sha256 == manifest$sha256
    ),
    Check = ifelse(
      all(
        exists &
          observed_bytes == manifest$bytes &
          observed_sha256 == manifest$sha256
      ),
      "PASS",
      "FAIL"
    )
  )
  manifest_objects[[index]] <- manifest
}
```

## Purpose and position in the analysis chain

Preparation 01 establishes the measurement record that all later preparation
steps use. The production workflow reads the fixed light-logger, sleep-diary,
and wear-log releases from nine study sites. It checks their identities,
converts the logger observations to complete one-minute values, preserves both
actual and local clock time, and assigns a measurement context to each minute.
Its outputs enter [Preparation 02](02_coverage_sample_flow.qmd), where hourly
and daily coverage is assessed.

The scientific inputs are 35 fixed local source files: light-logger,
sleep-diary, and wear-log files from recorded site releases. Their exact
release identities and file checks are documented in the technical sections
at the end of this page.

```{mermaid}

%%| fig-cap: "Position of Preparation 01 in the data-to-analysis chain. The report reads the stored outputs of these operations but does not execute them."

  A --> E["Prepare checked sleep<br/>and wear intervals"]
  D --> F["Align measurement context<br/>and validity flags"]
```

## 2. Preserve actual time and local clock time

Two time coordinates are retained because they answer different questions.
`datetime_utc` identifies the actual instant and is used to order readings and
measure elapsed time. `datetime_wall` represents the local clock reading, so
08:00 has the same time-of-day meaning at every site. At an autumn clock
change, one local minute can correspond to two actual instants. The stored
audit contains 360 such participant-level wall-clock minutes—120 for
Madrid (ES) near-eye data, 120 for Madrid (ES) chest data, and 120 for
Tübingen (DE) near-eye data.
They remain distinct in UTC and are not discarded or averaged during import.

The original logger interval is inferred separately for each participant and
placement. A one-minute value is retained only when all expected original
readings in that minute are present and finite. Table
@tbl-preparation01-aggregation-regimes shows the resulting regimes; the
production audits recorded no incomplete original-reading schedule.


## 3. Prepare sleep and wear periods

The sleep diary defines the interval from sleep preparation to wake. Its start
is included and its end is excluded. These measurements characterize the
bedside sleep environment and remain part of the intended hybrid 24-hour
record. The wear log supplies additional context. An `off` label while awake
is treated as true non-wear; `sleep` and `site_leave` labels are retained for
provenance but do not independently remove a light value.


## 5. Apply the melEDI operating limit

The valid melanopic equivalent daylight illuminance operating range is
strictly below 100,000 lx melEDI [@condor2023actlumus]. Values at or above
that boundary remain in the stored raw channel and receive an explicit flag,
but the analytical melEDI channel is unavailable for that minute. The rule
does not remove illuminance solely because melEDI reached its limit.


## 7. Checks that had to pass

The 35 fixed source files are recorded in
[`pinned_downloads.csv`](../../artifacts/12_manifests/pinned_downloads.csv).
Their repository revisions, DOIs, URLs, byte sizes, and SHA-256 digital
fingerprints are propagated to
[`source_audit.csv`](../../artifacts/02_aligned/source_audit.csv). A SHA-256
fingerprint establishes file identity; it does not describe scientific
contents.

::: {.callout-note appearance="simple" title="What is calculated during this render?"}
This report reads already stored CSV manifests and audits. During rendering it
checks the existence, byte size, and SHA-256 fingerprint of every listed
Preparation 01 artifact and fixed source file; checks the columns needed for
the displays; and calculates only compact descriptive totals from stored audit
rows. It does not retrieve a source file, import logger data, aggregate a
minute, align a diary or wear period, replace a signal value, rebuild an
artifact, or run the production verifier.
:::

The stored audits expose the checks performed during production. Rendering
does not rerun their producing verifier; it confirms the identities of the
stored evidence and summarizes the recorded outcomes.
