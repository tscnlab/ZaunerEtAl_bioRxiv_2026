Preparation 05: Acquire fixed questionnaire and diary inputs

From site-specific data releases to locally verified analysis inputs

Last modified:

August 12, 2026

Purpose and position in the preparation chain

Preparation 05 obtains the fixed questionnaire and diary files needed for participant characteristics, chronotype, habitual light-exposure behaviour, visual light sensitivity, exercise, self-reported lighting context, and sleep. Each site’s files come from a fixed data release. The result is a local, verified copy of every expected file, plus stored descriptions of each object’s rows and columns. Exact repository, release, and file-identity details are collected in the technical provenance section.

This step does not clean variables, calculate scores, harmonize factor levels, interpret timestamps, join participants to light metrics, or filter a model sample. Preparation 06 performs those operations from the fixed files recorded here. The light-exposure metrics from Preparation 04 form a separate input branch into Preparation 06.

flowchart LR
  S["Fixed questionnaire<br/>and diary releases"] --> A["Preparation 05<br/>acquire and verify files"]
  P1["Preparation 01<br/>nine verified sleep diaries"] --> A
  A --> L["63 local questionnaire<br/>and diary objects"]
  A --> U["Object and column audits"]
  L --> P6["Preparation 06<br/>normalize and join inputs"]
  U --> P6
  P4["Preparation 04<br/>light-exposure metrics"] --> P6

Files acquired and why

The availability record contains all 63 combinations of nine sites and seven modalities. Its explicit grid matters because a missing download cannot be mistaken for an intentionally unavailable questionnaire. The record can carry a reason for an expected absence, although no current entry is absent.

Access, privacy, and acquired contents

The acquisition audit records structure rather than displaying participant responses. Row counts below describe the unchanged objects across all nine sites. Preparation 06 later decides how columns are interpreted and which ones may enter an analysis.

The 63 objects contain 963 recorded columns in total. That count is a schema audit, not a claim that all columns are suitable for analysis. In particular, raw free-text fields remain in the untouched source objects but are not shown here; Preparation 06 explicitly excludes them from analytical outputs.

Technical provenance

NoteWhat is calculated during this render?

Rendering reads the stored registries, acquisition manifest, object audit, and column audit. It checks their schemas, hashes the 63 already local files, compares the nine sleep diaries with the Preparation 01 inventory, and calculates compact row and file totals. It does not connect to the network, open raw questionnaire values, run the acquisition builder or verifier, normalize a variable, construct a model input, or overwrite any stored artifact.

Input specification records

Fixed source releases

All download addresses embed the recorded commit. None contains /main/ or another moving branch label. Consequently, revisiting the same address refers to the same repository state rather than whatever happens to be current at a later date.

Corrected Munich (DE) exercise source

One file deliberately uses a modality-specific commit instead of the default Munich (DE) release. The upstream exercise diary corrects the participant identity at the source; Preparation 05 does not rewrite that identifier locally.

How files were obtained in the recorded run

The recorded run reused 62 files and downloaded one. The reused files comprise nine sleep diaries from Preparation 01 and 53 files from the verified model-input cache. Reuse is not based only on a filename: the release identity, local path, byte size, and SHA-256 must all agree. A SHA-256 is a digital fingerprint; changing even one byte changes the fingerprint with overwhelming probability.

Production sequence

Separating the expected-file specification from cache or download decisions prevents local availability from defining the scientific input. Separating object/column inspection from later normalization likewise ensures that a changed upstream schema is visible before values are interpreted or joined.

Exact stored artifacts passed to Preparation 06

The local RData objects remain separated by site and modality. Preparation 05 does not combine sites, rename values, recalculate questionnaire scores, select categories, or discard incomplete intervals. The manifest and audits allow Preparation 06 to perform those operations against known, immutable inputs.

Checks tied to the current stored files

All 63 local files match the acquisition manifest with SHA-256 ac79a83c2d60dde1ac563f6e2cb09c58d4d7d3b06549d9b9262e4acd5a50a58b. The nine sleep diaries also match the Preparation 01 inventory independently on repository, commit, DOI, address, local path, fingerprint, and bytes.

Stored independent verification

The exact-current verification record is documented in the detailed input-provenance record and the normalization verification record. The verifier is not rerun during this reader-facing render. It establishes that the fixed source objects reached normalization without an unrecorded release or schema change. It does not establish a hypothesis result, model sample, effect estimate, or scientific claim.

absolute_path <- function(path) {
  ifelse(grepl("^/", path), path, file.path(root, path))
}

relative_path <- function(path) {
  sub(paste0("^", root, "/"), "", path)
}

read_stored_csv <- function(path) {
  full_path <- absolute_path(path)
  stopifnot(file.exists(full_path))
  readr::read_csv(full_path, show_col_types = FALSE, progress = FALSE)
}

assert_columns <- function(data, required, label) {
  missing_columns <- setdiff(required, names(data))
  if (length(missing_columns) > 0L) {
    stop(
      label,
      " is missing required columns: ",
      paste(missing_columns, collapse = ", ")
    )
  }
  invisible(data)
}

prep_gt <- function(data, source_note = NULL, groupname_col = NULL) {
  output <- gt::gt(data, groupname_col = groupname_col) |>
    gt::opt_row_striping() |>
    gt::sub_missing(missing_text = "—") |>
    gt::tab_options(
      table.font.size = gt::px(13),
      table.width = gt::pct(100),
      data_row.padding = gt::px(4),
      heading.align = "left",
      source_notes.font.size = gt::px(11)
    )
  if (!is.null(source_note)) {
    output <- output |>
      gt::tab_source_note(gt::md(source_note))
  }
  output
}

## Purpose and position in the preparation chain

Preparation 05 obtains the fixed questionnaire and diary files needed for
participant characteristics, chronotype, habitual light-exposure behaviour,
visual light sensitivity, exercise, self-reported lighting context, and
sleep. Each site's files come from a fixed data release. The result is a local,
verified copy of every expected file, plus stored descriptions of each
object's rows and columns. Exact repository, release, and file-identity details
are collected in the technical provenance section.

This step does not clean variables, calculate scores, harmonize factor levels,
interpret timestamps, join participants to light metrics, or filter a model
sample. [Preparation 06](06_model_ready_datasets.qmd) performs those operations
from the fixed files recorded here. The light-exposure metrics from Preparation
04 form a separate input branch into Preparation 06.

```{mermaid}
flowchart LR
  S["Fixed questionnaire<br/>and diary releases"] --> A["Preparation 05<br/>acquire and verify files"]
  P1["Preparation 01<br/>nine verified sleep diaries"] --> A
  A --> L["63 local questionnaire<br/>and diary objects"]
  A --> U["Object and column audits"]
  L --> P6["Preparation 06<br/>normalize and join inputs"]
  U --> P6
  P4["Preparation 04<br/>light-exposure metrics"] --> P6
```

## Files acquired and why

The availability record contains all 63 combinations of nine sites and
seven modalities. Its explicit grid matters because a missing download cannot
be mistaken for an intentionally unavailable questionnaire. The record can
carry a reason for an expected absence, although no current entry is absent.

## Technical provenance

::: {.callout-note title="What is calculated during this render?"}
Rendering reads the stored registries, acquisition manifest, object audit, and
column audit. It checks their schemas, hashes the 63 already local files,
compares the nine sleep diaries with the Preparation 01 inventory, and
calculates compact row and file totals. It does **not** connect to the network,
open raw questionnaire values, run the acquisition builder or verifier,
normalize a variable, construct a model input, or overwrite any stored
artifact.
:::
